# 可用性与排队共用的自动回退设计

2026-10-21，新增需求设计；本轮代码落地与兼容契约见[08](08_自动回退代码落地与兼容契约.md)，功能完成状态以实现审计/测试记录为准。依据用户新增要求：本地 Codex CLI 或其他生图工具不可用时，Bridge 告知 Alchemy，暂时转传统 Sub2API；恢复后自动切回，并与排队回退共用判断。

本设计只替代 v1.2 对**明确开启本策略的新请求**的 bridge_only 限制。不修改未选择 Bridge 的原任务，不放松“已执行/执行不明禁止另起一次生成”，也不声称已有排队自动回退代码。旧客户端、关闭策略及原有试用任务保持原行为。

## 1. 用户看到什么

现有管理员 Bridge 卡片增加一个默认关闭的开关：**本地繁忙或不可用时，自动使用云端生图**。

开启说明：会使用原 Sub2API 账号及原计费规则，参考素材可能发送至该已配置云端；遵守原账户权限、余额、预算和素材外发限制。没有可用云端配置时不能假装切换成功。不展示复杂状态机或要求用户填写技术参数；管理员开关不替代用户原有费用/素材授权。

只显示三种主提示：
- 本地可用，优先本地生图。
- 本地暂不可用/等待过久，已临时使用云端。
- 本地已恢复，新任务自动回到本地。

排队等待阈值放在折叠高级设置，建议初值 30 秒，最终以实现验收配置为准。界面不承诺两个渲染器产生相同风格或像素。

## 2. 两端职责和信号

- Agent 检测已配置工具并上报 Bridge；它不自行登录账号、管理或复制凭据，不做付费探测、不替 Alchemy 选 Sub2API。可选账户状态检查可能由用户自己的 CLI 刷新已有登录，须显式启用并告知，详见08。
- Bridge 汇总每个 workspace/profile 的实时可用性、容量和原因，提供版本化 HTTP 状态信号；它不持有 Sub2API 密钥，也不修改 Alchemy 账单或默认模型。
- Alchemy 的新增路由适配器消费信号、结合队列等待和原业务许可，决定新请求走哪条路径。所有输出仍交给原 Alchemy 审核/历史/交付权威。
- 首版复用已有 Agent 心跳和 Alchemy 有界轮询，在能力响应中协商新增 `routing_availability_v1` 描述；不增加 Bridge 向 Alchemy 的第二路回调，也不要求共享存储；首轮部署同在用户Windows电脑、loopback HTTP，后续才是可选双VPS。
- 设计建议：Agent 每 30 秒报告，Bridge 90 秒未收到则标记失联；Alchemy 按 5 秒有界周期读取信号并缓存，遵守 Retry-After。这些是可配置设计默认值，不是现成实现证明。

建议每个 profile 信号包含：schema_version、profile_id、profile_revision、单调 revision、observed_at、valid_until、health（available/unavailable/unknown）、capacity（idle/busy）、reason_code、retry_after_seconds、evidence_kind。通过现有认证限制 workspace，不包含日志原文、prompt、凭据或账户详情。Alchemy 用本机接收时刻的有限 TTL 辅助判陈旧，不能仅信远端时钟。

健康信号必须与管理员 enabled/draining/disabled、节点 active/revoked 及真实工具验收资格分开。管理员暂停、关闭或撤销是明确操作意图，不能当作故障自动绕过，也不能因心跳恢复自行开启。乱序/陈旧修订号忽略，服务重启不让状态修订回退。

信号只控制**后续选路偏好**，不是某个任务“从未执行”的证明。旧 Bridge 不支持该描述时，不启用自动策略，继续原 bridge_only 行为。

## 3. 什么算不可用，如何恢复

健康与忙碌分开：工具健康但正在执行属于 busy，不算工具损坏；人工 MJ 等待用户本身也不算故障。

可以无生图探测的项目：已配置 CLI 是否存在、受支持版本/协议、必要本地资源及进程健康；登录/额度只有受支持的只读状态或已有明确错误证据才能判断，不能凭空猜测。具体执行中的错误必须区分“工具全局不可用”与“这次输入/尺寸/审核失败”。后者不把整个 profile 判坏。

- 明确缺失工具、明确登录失效、受支持接口返回确定额度耗尽：立即 unavailable。
- 网络/进程短暂异常：建议连续 2 次失败后 unavailable；心跳过期为 unknown/offline。
- 工具已知不支持当前参数：任务能力不匹配，不自动删掉参数、降低质量要求或让全局健康变红。
- 自动执行结果不明：该任务进入对账，不能因为心跳又正常就另起一次。

恢复应验证**原故障原因**已解除。连续 2 次有效成功报告、并至少稳定 60 秒后恢复本地优先，避免反复切换。只有 CLI --version 成功不能清除“登录失效/额度耗尽/图像工具未验证”。无可靠只读恢复证据时显示“需确认恢复”，允许操作者单独授权一次真实验证；不能偷偷付费生图作为心跳。未通过真实图像能力验收的 profile 仍不能自动宣称恢复可用。

健康按 profile 隔离：Codex 故障不把人工 MJ 或其他工具一起判为故障。首版不新增未经授权的工具间自动轮换。

## 4. 与排队共用一个选路器

新增一个 Alchemy 侧 RoutingPolicy，输入是原请求、用户策略、profile 信号、排队时间和云端兼容性；输出仅为 route/wait/reconcile，带稳定原因码。不分别写“故障回退”和“排队回退”两套执行器。排队预算依据实际入队事实和 Alchemy 单调计时累计，不能用 busy 一次报告直接判超时；重启保留已等待预算，不因重复查询重置。

| 条件 | 动作 |
|---|---|
| 未开启自动策略/用户要求仅本地 | 保持原路径，给出等待或故障提示 |
| 本地健康且有容量 | 为新任务选择 Bridge |
| 本地忙、等待未超阈值 | 保持有界等待，不新建云端任务 |
| 等待超阈值、工具不可用或信号失效，且尚未提交 Bridge | 在原权限/预算/素材允许且能力匹配时选传统 Sub2API |
| Bridge 已排队但尚未开始 | 必须先取得第 5 节原子退队证明，再选择云端 |
| Bridge 创建响应丢失，无法确认是否已入队 | 按原 origin_key 查询；查清前不转云端；一次查询 404 不证明迟到 create 不会成功 |
| 已获 start grant、人工任务已交用户、已有原图或执行状态不明 | 不自动转云端，继续同任务恢复/对账 |
| 云端不可用、无预算、禁止外发或不支持冻结要求 | 明确等待/失败提示，不放宽约束、不循环切回本地重试 |

Alchemy 访问不到 Bridge 时：可以对**确认尚未尝试提交的后续新请求**选云端；已发出的请求不能用“连不上”作为未执行证明。

## 5. 排队退队和一次生成

复用既有取消事务的基本结构，但新增明确的、幂等的 **withdraw-before-start** 合同。不能只看到现有 canceled 字段就放行云端，因为人工任务即使已交用户也可能显示 canceled。

Bridge 在同一事务内与 start/manual-ready 争用同一任务权威：确认不存在任何 start/manual grant、没有 receipt、没有可能已执行事实；把任务永久标记为“未开始且已撤回”，拒绝迟到的派发/start，并返回不可变撤回确认。若已经开始/人工交付/结果不明，返回不可撤回状态。重复请求返回相同确认，响应丢失可用稳定 withdrawal_key 查询，不产生新 task。证明必须绑定原 origin/task/attempt/intent 摘要。若将来允许撤回仍在传输中的 create，须先实现按 origin 的持久禁止创建记录，使迟到 create 也无法执行；首版没有该能力就保持对账等待，不能根据一次 404 切路。

Alchemy 持久保存 request_id、origin_key、route_generation、已选 route、remote_task_id、withdrawal_ref、cloud_job_ref 和切换原因。同一 intent 使用锁/CAS 保证只有一个恢复进程取得派发权。先记意图再外调。只有“从未发出 Bridge 请求”或“明确撤回确认”才可给原业务创建云端任务。

云端也必须使用既有可查询的幂等提交接缝：重复点击、崩溃重启、提交回包丢失仍返回同一 cloud_job_ref。若现有 Sub2API/宿主接缝不能提供这种保证，先补受支持的窄接缝，不能靠重复 POST 碰运气。一次用户请求只允许一条仍有执行可能的链路。

## 6. 恢复后“切回来”的准确含义

恢复信号只把**未来尚未选路的新请求**恢复为 Bridge 优先。

已经转到 Sub2API 的任务继续云端完成，不取消重做、不把结果搬回本地再生成；已经安全撤回的旧 Bridge 任务永不复活。正在本地执行或执行不明的旧任务独立恢复，不被路由偏好覆盖。Alchemy 重启必须读取持久选路记录，而不是按当前健康重新选择旧任务。

## 7. 与现有 V3 试用及传统链路的接缝

目前普通 Generate 没有 Bridge 路由选项，现有桥接入口是单图、开发态、review-only；故此需求是**新增路由开发阶段**，不是把现有心跳灯改成自动切换即可。

实现须新增一个明确的“本地优先，必要时云端”请求模式，默认普通 Generate 不变。适配器只决定渲染路径，Alchemy 原规划/用户要求保持权威，不把两次 Brain 规划的不同请求当成同一任务。云端复用现有受支持的生成、权限、计量、审核、历史及交付服务，不复制它们的业务规则。

原试用入口不因回退而获得正式交付资格；相同请求的结果待遇不能因走本地或云端随机变化。要开放生产模式必须单独满足真实工具验收和现有生产准入，不能靠移除 development_only 来实现。任务模式与费用提示在提交前确定，并绑定选路记录。

仅在云端能力可满足冻结的 prompt/有序参考图/尺寸等约束时回退。若无法等价承接则提示，而不是静默剥离参考图、重写硬性要求。V2、其他模板和 Video 需要各自原生适配，不借用 V1/V3 后端。

## 8. 开发拆分与验收

1. Bridge：按 profile 的探测与持久健康报告、信号修订号和过期语义、受支持描述；不添加第二个调度器。
2. Bridge：幂等原子退队证明，覆盖与 start/manual-ready 并发及丢包重查。
3. Alchemy：独立 RoutingPolicy、持久选路记录、复用队列阈值与健康回退、原 Sub2API 幂等接缝；保留默认关闭。
4. 管理员：一个易懂开关、折叠阈值和原预算授权提示、三个主状态；现有卡片排版不变。
5. 云端模拟：缺 CLI/登录失效/额度耗尽/网络断开/仅忙碌/恢复抖动/信号乱序与过期；不进行真实账号探测或付费生成。
6. 核心验收：新请求自动退到云端，恢复后新请求回本地；排队退队和 start 竞争只能一方获准；请求/取消/回退响应丢失、重启及重复消息不造成两次生成/计量；已开始/unknown/人工已交付不自动重生图；关闭开关和旧客户端保持原行为。
7. 默认链路、权限/素材/预算、审核/选图/导出回归；实机验证仍在云端开发完成后进行。
